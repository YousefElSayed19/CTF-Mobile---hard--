# Validation report — NexaWallet

## Status: author-verified end-to-end; two minor open items

The full solve chain has now been run end-to-end by the author against a
freshly rebuilt APK, recovering the correct flag. This report tracks
what has been independently verified and what (small) items remain open,
consistent with how this catalog's other binary-track lab (`dual-check`)
was tracked.

## What was verified in this authoring environment

- **Flag format:** `duck{q68s_aehr341rbyn0cc87flkraa0hnmy}` matches
  `^duck\{[a-z0-9_]{16,40}\}$` — checked with Python's `re` module.
- **`flag_hash` correctness:** SHA-256 of the exact flag string equals
  `17166ae75476ab1231632df6a4e7d3648d7f2d9453839e885f576eebc4dfd4eb`,
  matching `lab.yml` — checked with Python's `hashlib`.
- **The obfuscated constant round-trips correctly:** the `ENCODED_FLAG`
  Base64 string in `TransferAuthorizer.kt`, XOR'd with `0x5A` byte-by-byte,
  decodes to exactly the flag above — verified independently in Python
  before the Kotlin was written, and re-verified against the final
  committed source.
- **The fix does not reintroduce the original non-determinism bug:**
  `mintClearanceToken()` no longer reads `username`, `amount`, or
  `System.currentTimeMillis()` — confirmed by reading the final source
  (it ignores both parameters entirely and returns the same decoded
  constant every time).
- **`check.py` logic:** matches the pattern already validated for
  `dual-check`'s checker (stdlib-only, reads `flag_hash` from `lab.yml`,
  enforces the format regex before hashing) — same script structure,
  adapted paths/values only.

## The accepted static-shortcut trade-off

As documented in `challenge-design.mdx` and `official-solution.mdx`: a
sufficiently determined static reader who locates
`TransferAuthorizer.ENCODED_FLAG` and its `XOR_KEY` can decode the flag
offline, without running the app or defeating either gate. This was
weighed deliberately, not discovered as an afterthought:

- The flag **must** be fixed (one value, one `flag_hash`) — a hard
  catalog requirement, confirmed with the author via an explicit
  three-way choice (fixed flag / document as a known limitation / hybrid
  design); the author chose a fixed flag.
- A **fixed** value embedded in client-side code is, by the same
  principle this catalog's `dual-check` lab's own technique pages teach
  (`aes-key-derivation-from-split-secrets.mdx`,
  `chained-byte-transform-reversing.mdx`), always statically recoverable
  by a sufficiently motivated reader — no obfuscation scheme changes that
  fact, only the effort required.
- Given that, the chosen design (XOR+Base64, not plaintext) at minimum
  defeats a trivial `strings`/quick-read scan, which was judged
  sufficient given the catalog-wide, already-established norm that
  client-side protections raise cost rather than prevent extraction.

**Recommendation for the maintainer review:** accept this as a documented
trade-off consistent with the rest of the catalog's binary-track design
philosophy, rather than requiring a server-side component be added solely
to close it (which would change this lab's delivery model from BYOD
artifact to a hosted service, a larger scope change than this submission
is intended to make).
