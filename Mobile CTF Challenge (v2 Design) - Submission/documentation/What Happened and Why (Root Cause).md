# What Happened and Why (Root Cause)

## The core issue, in one sentence

Every security decision in NexaWallet — whether the device is being tampered with, and whether a transfer above the limit is authorized — is computed and enforced **entirely on the client**, inside an environment the attacker fully controls. No server ever independently verifies any of it.

This is the central lesson the challenge is built to demonstrate. Everything below is a specific consequence of that one design choice.

---

## 1. Instrumentation detection is a deterrent, not a boundary

`IntegrityGate` correctly and deterministically detects an active Frida session (loopback port, injected-library signature in `/proc/self/maps`, suspicious thread names). All three checks work as designed and have zero environment-dependent false positives — a genuinely important property for a *fair* challenge, but it says nothing about *security*.

The reason this is still bypassable has nothing to do with a bug in the detection logic itself: it's that the code performing the check, the code consuming its result, and the attacker's tooling all run in the **same process, at the same privilege level**. Once an attacker can execute arbitrary code inside that process (which dynamic instrumentation is, by definition), they can intercept, skip, or rewrite any decision that process makes about itself — including any future, more sophisticated version of this same check. There is no code a client-side detector can write that a sufficiently privileged attacker inside the same process cannot eventually neutralize; it can only raise the cost and time required.

A secondary, interesting *implementation* detail discovered during solving reinforces this: even the straightforward approach of hooking the app's own `isTampered()` wrapper function failed silently, because ART's inlining folded that small function directly into its caller at the bytecode/JIT level, leaving no runtime call boundary for Frida to intercept. The actual fix — hooking the underlying framework methods instead — is a *technique* refinement, not a *security* one: it does not change the fundamental fact that detection running client-side is advisory information at best, not an access-control mechanism.

## 2. A non-exported hidden Activity is security by obscurity, not access control

`ReviewGateActivity` is declared `exported="false"` and is never referenced from any other component in the app. This genuinely does prevent two specific attack surfaces: another installed app launching it via an `Intent`, and `adb shell am start` launching it externally through the OS's component-resolution path. Both of those are legitimate, real protections that `exported="false"` is designed for and does provide.

What it does **not** protect against is an attacker who already has code execution inside the app's own process — at that point, `startActivity()` is just a normal method call on an object (the app's `Context`) the attacker already holds a reference to, with no OS-level permission check standing between them and it. "Nobody will find this Activity because nothing links to it" is a statement about discoverability, not about enforceability, and the two are not the same thing once static analysis (reading the decompiled manifest and code) makes discovery essentially free.

## 3. The authorization state has no origin it can prove

`ReviewState.isCleared` is a boolean living in process memory, set only by `ReviewState.grantClearance(activity)` — which does check that the passed-in object is a live, non-finishing `Activity` instance, specifically to prevent a bare `ReviewState.grantClearance(null)`-style one-liner from working. That check raises the bar meaningfully (it's why the Walkthrough's advanced path still has to go through `Java.choose()` to obtain a genuinely live instance rather than fabricating one), but it answers "is this a real Activity instance?", not "did a legitimate human reviewer actually approve this?". Nothing cryptographically ties `isCleared = true` back to any actual decision made by anyone outside the compromised process — because there is no one outside the process in this design to make that decision.

## 4. The proof of success is minted by the same party being tested

`TransferAuthorizer.mintClearanceToken()` computes the flag from values the app itself already holds (username, amount, a coarse timestamp, and a secret string embedded in the APK). Once reverse-engineered, the exact formula could be replicated entirely offline, with no interaction with the running app at all, by anyone who extracted the embedded secret from the APK. The "proof" that a privileged action was authorized is generated by — and only verifiable relative to — the exact same client that is not trusted to make the decision to authorize it in the first place. A legitimate system's proof of authorization should come from the one party in the system the client cannot impersonate: a server it does not control.

---

## The pattern underneath all four points

Each mechanism independently delays or complicates an attack. None of them, individually or combined, changes the category of problem: **a decision made and enforced entirely within an environment the user controls cannot be relied upon by anyone who does not also control that environment.** This is the general principle NexaWallet is built to illustrate concretely, and it's the same principle that applies to anti-cheat in games, DRM, and client-side-only payment validation in real mobile apps.
