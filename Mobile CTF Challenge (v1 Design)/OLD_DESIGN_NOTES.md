# NexaWallet CTF — ملاحظات على التصميم القديم (Legacy Design Notes)

## السياق

النسخة القديمة من تحدي NexaWallet كانت بتعتمد على 4 نقاط فحص منفصلة لمنع اللاعب من الوصول للفلاج:

1. `RootFridaDetector.checkRootFiles()` — فحص وجود ملفات `su` معروفة
2. `RootFridaDetector.checkFridaPort()` — فحص بورت 27042 (frida-server الافتراضي)
3. `MapsIntegrityCheck.isMemoryTampered()` — فحص `/proc/self/maps` بحثًا عن مكتبات محقونة
4. `TransferActivity.validateOp()` — فحص إن المبلغ المطلوب تحويله أقل من أو يساوي الحد المسموح

## المشكلة الأساسية

المشكلة مش كانت في **عدد** الفحوصات، كانت في **نوع** الفحص الأول تحديدًا.

فحص `checkRootFiles()` كان بيعتمد على **حالة البيئة** (الإيميوليتور المستخدَم) مش على **فعل اللاعب نفسه**:

```kotlin
private val SUSPICIOUS_PATHS = arrayOf(
    "/system/app/Superuser.apk",
    "/sbin/su",
    "/system/bin/su",
    "/system/xbin/su",
    ...
)

private fun checkRootFiles(): Boolean {
    for (path in SUSPICIOUS_PATHS) {
        if (File(path).exists()) return true
    }
    return false
}
```

كتير من صور الإيميوليتور (خصوصًا صور AOSP/Google APIs القديمة اللي بتيجي rooted by default لتسهيل التطوير) بييجي معاها ملف `su` موجود فعليًا على الجهاز، **حتى لو اللاعب مش مستخدم Frida ولا أي أداة تحليل أصلاً**.

النتيجة: لاعب بيفتح التطبيق على إيميوليتور عادي تمامًا، من غير ما يلمس Frida، بيتوقف فورًا عند شاشة "Tampering Detected" — ويفتكر إن المشكلة في الكود أو في إعداد جهازه، فيضيع وقت كبير في تشخيص مشكلة مالهاش علاقة بمهارته أو بالتحدي نفسه.

### ليه ده عيب تصميمي خطير؟

- **بيدي انطباع غلط للاعب**: بيفكر إن فيه مشكلة في فهمه أو في setup بتاعه، مش إن فيه false positive في الفحص نفسه.
- **التحدي مش قابل للتكرار بشكل متسق**: نفس اللاعب على إيميوليتور تاني (مثلاً AVD رسمي بصورة "Google APIs" من غير su) ممكن يعدي الفحص من غير ما يفهم ليه أصلاً، وده بيكسر مبدأ "الصعوبة لازم تيجي من مهارة اللاعب مش من عشوائية البيئة".
- **بيضيع وقت تشخيصي كبير**: جزء كبير من وقت أي لاعب هيتاكل في محاولة فهم "ليه الفحص بيترفض" بدل ما يركز على التحدي الفعلي (bypass الكشف واستخراج التوكن).

## كان ممكن نصلحها بتعديل بسيط

الحل المباشر كان تعديل سطر واحد فقط — فحص **صلاحية التنفيذ** بدل **الوجود فقط**:

```kotlin
private fun checkRootFiles(): Boolean {
    for (path in SUSPICIOUS_PATHS) {
        val f = File(path)
        if (f.exists() && f.canExecute()) return true
    }
    return false
}
```

ده كان كافي يحل الـ false positive من غير ما نلمس أي جزء تاني من التصميم.

## ليه قررنا نبني من الصفر بدل كده؟

**القرار ده تصميمي مش إجباري تقني.** المشكلة الأصلية (false positive بتاع su) كانت قابلة للحل بتعديل بسيط. لكن احنا استغلينا الفرصة عشان:

1. **نرفع مستوى الصعوبة بشكل متعمد**: بدل 4 نقاط فحص مشتتة بين كلاسات مختلفة (`RootFridaDetector`, `MapsIntegrityCheck`, `validateOp`)، نبني تصميم أنظف بعدد نقاط أقل لكن كل نقطة أعمق وأصعب فعليًا.
2. **نضيف نوع تحدي جديد غير Frida hooking البسيط**: زي استكشاف بنية التطبيق (AndroidManifest، Activities غير مرتبطة بمسار UI طبيعي، Intent navigation)، عشان الحل مش يبقى مجرد "اعمل hook على كل boolean تلاقيه".
3. **نتجنب الاعتماد على حالة البيئة نهائيًا**: كل فحص في التصميم الجديد لازم يكون **حتمي** (deterministic) — بيتفعل بس كنتيجة فعل حقيقي من اللاعب (تشغيل Frida فعلاً)، مش كنتيجة لظروف الجهاز.

## الخلاصة

النسخة القديمة متسيبتش لأنها "معطوبة بشكل مينفعش يتصلح" — كانت قابلة للترقيع بسهولة. الانتقال للتصميم الجديد قرار واعي بالابتعاد عن الترقيع لصالح بناء نظام فحص أنظف من جذوره، بمفاهيم ومسميات مختلفة بالكامل، يخدم هدف "تحدي هارد لكن عادل" بشكل أفضل من تصحيح تدريجي لتصميم قديم.
